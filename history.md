# History: Learning Factory

Short entries with insights and fun facts about building this with Claude Code, for the POC presentation.

## 2026-11-15 · Fifth pass (#7, #3): two issues in parallel, and the CI runner as a stand-in server

- **Two issues at once, one conductor.** The manager claimed #7 (lab sessions) and #3 (server bootstrap) together. Each got its own git worktree, exam writer, implementer and reviewer, and the agents ran side by side. 2 PRs merged in about 70 minutes, with 4 review rounds and 6 CI rounds between them.
- **The exam found a real production bug on its first run.** The two lab containers started first took the manager's fixed address 172.31.240.2. A lab started while the manager restarts would do the same. Fix: one `--ip-range` flag, so labs only get addresses from .128 up.
- **"Dangerous" code gets a rehearsal server.** The bootstrap edits the shared production server, where the owner's n8n, OpenClaw and client apps run. CI runs the real script with sudo on a throwaway GitHub runner: twice, with a foreign "sentinel" container whose start time must not change, a pre-seeded daemon.json key that must survive byte for byte, and a baseline that fails right after the first step, to prove the rollback. The first run on the real server was a dry run, and it printed exactly the plan.
- **Reviewers found what the tests couldn't.** Installing the `runsc` package would have edited daemon.json and reloaded Docker *by itself*, outside every safety step. `apt` over SSH could have restarted the owner's services through needrestart. A student could fill the host disk through `/tmp`. Each finding became a test first, then a fix.
- **Evidence beat assumptions about gVisor.** `sudo` failed in sudo labs. Three diagnostic CI runs showed it was not the capabilities, the mounts or the flags: a setuid-root copy of perl stays at uid 1001 under gVisor and becomes root under runc. Running those labs on runc would weaken the isolation the spec makes a condition for using the server, so the factory recorded the evidence (D26), filed #47, and did not quietly weaken the sandbox.
- **Discipline costs PRs, not quality.** The per-commit exam gate allows test changes only before the code, so a fix to the exam after the code meant re-sequencing onto a new branch and a new PR. #7 went #41 → #43 → #48, and #3 went #42 → #45 → #46. Nothing was force-pushed, and every merged PR has its exam commits first.
- **A Docker quirk worth knowing:** `systemctl reload docker` reloads runtimes only when the `runtimes` key is present in daemon.json. Deleting the key leaves the old runtime registered in memory, so rolling back means writing `"runtimes": {}`, reloading, and only then restoring the original bytes.

## 2026-11-15 · Factory pass lf-q4r8: two PRs while the next exam was being written

- **Pipelining agents.** While CI ran on the bootstrap PR, the next issue's exam writer was already working in its own worktree. Then the reviewer of one PR and the implementer of the other ran at the same time. Two PRs reviewed and merged in about 80 minutes, with the manager mostly waiting on CI.
- **Check the test counts, not just the green tick.** A 4-minute docker job for about 9 real bootstrap runs looked too fast. Comparing with main settled it: 63 docker tests before, 87 after, exactly the 24 new ones, and none skipped.
- **Detaching a script opens a new hole.** Running the server script with `setsid nohup` (so a cancelled job can't kill it halfway through a rollback) means a second run can start while the first is still alive. Bash reads a running script from disk as it goes, so `scp` over it can make it run arbitrary bytes. The reviewer caught it. Fix: a per-run directory and a `flock` taken on the server.
- **When two requirements conflict, write the decision down.** "Leave daemon.json alone" and "runsc must have its runtime arg" can't both hold when the runtime was registered by a dockerd flag (flags can't carry runtime args). The script now fails safe with one exact owner step instead of risking a daemon that won't start after the next reboot (D29).

## The laptop that slept through a deadline (2026-11-15)
- The night pass started at 02:56, the laptop slept, and on waking at 08:52 the runner saw "6 hours" on the wall clock and called it a timeout. `Stop-Job` stopped the PowerShell job but **not** `claude.exe`, so the manager kept working without a runner. Four minutes later the scheduler started a second manager in the same worktree.
- Fix: the limit now counts awake time only (a gap of more than a minute between ticks = sleep). A timeout kills the manager's process tree, and the runner never starts while a manager process is alive.
- Insight: on a laptop, "wall-clock time" and "work time" are different things, and stopping a wrapper is not stopping the process inside it. The live view showed it at once: a worker marked "busy" after the pass was marked "ended".

## 2026-11-15 · Factory pass lf-ce139: a five-variant experiment instead of a theory

- **Change one thing per variant.** Lab containers kept dying on the server, and the suspects were runsc, the pinned gVisor build, the lab network, or the test workload. One script started six containers that each differed in a single way (PID 1 `sh`/tini/`sleep`, probe with or without busybox `timeout`, lab network or default bridge, runsc or runc). Three minutes later the answer was clear: only `sh` as PID 1 plus a busybox `timeout` exec died, **under runc too**. It was the busybox test workload, not the sandbox, and the real labs (tini) were never at risk. The next isolation smoke passed all 21 checks (4 skipped: the gateway answers on none of the ports).
- **The reviewer made the experiment honest.** Round 1 caught that the first version would have counted "failed to start" as "died", had no runc control, and read the journal in local time. Any of these could have pointed the #13 decision the wrong way.
- **Shared worktree, shared HEAD.** Another session committed a state update in the same worktree while a feature branch was checked out, then ran `git push origin HEAD:main`, and the unreviewed feature commit went to `main` with it. GitHub then marked that PR "merged", so the review fixes needed a new PR. Lesson: check `git branch --show-current` before any commit in a checkout another session may use.
- **Ask the database, not the docs.** The open security question ("can our role run privileged functions in the shared Supabase DB?") was settled by a 40-line catalog query, run as that role in a `begin transaction read only` block through a dispatch-only workflow. Answer: none. The reviewer's catch: a transaction pooler may silently drop `PGOPTIONS`, so the read-only guarantee has to live inside the SQL.
- **Exam integrity also counts `pyproject.toml`.** The exam writer added a test dependency in the exam commit, and the per-commit gate rejected it ("exam and non-test code together"). The fix is a re-sequenced branch: exam files alone first, then dependencies and code.

## 2026-11-15 · Factory pass lf-a7d42: print the bytes before guessing

- **One diagnostic run beat two theories.** The terminal-proxy exam failed with "no `hi`" and two suspects (`su` broken under gVisor, or input typed too early). A throw-away draft PR printed every WebSocket frame, `ps`, the container's capabilities and a `su - student -c id`. Five minutes later: `su` works, the prompt arrives within a second, and input typed before it is **dropped, not buffered**, under runsc. Typed after the prompt, `echo hi` works. The test now waits for the prompt, as a person would (D33).
- **Then the bytes caught a second bug.** The exam expected `\nhi\n`, but real bash sends `\n ESC[?2004l \r hi`: it switches bracketed-paste mode off between the command line and its output. The diagnostics had printed exactly those bytes; the new pattern was checked against them locally before any CI run.
- **Exam fixes cost a branch each.** The per-commit exam gate accepts test changes only before code, and force-push is off. Each exam fix meant a new branch: exam, fix, cherry-picked code, new PR (#66 → #70 → #73 → #74). Annoying, but it keeps "the exam was written before the code" true.
- **Slice before you build.** The deploy issue had grown to nine acceptance items. The manager split off the container image and compose file (#72, D32), and its exam writer and implementer ran while the terminal PR waited for CI: two PRs green in parallel.
- **Shell quoting is a trap on Windows.** Here-doc Python with `\r` edits silently failed to match, twice: the shell layer ate a backslash. Exact edits through the file-edit tool, and a check script run against the real captured bytes, worked first time.
- **The gate caught the manager, too.** The #72 follow-up put an exam file and a `ci.yml` change in one PR, and the exam gate refused it, which is exactly the rule (D19) the manager had written down a day earlier. The fix: code and CI first, then the exam in its own PR. Stacking the exam as a draft on the code branch let CI prove it against that code before the merge (320 acceptance tests, up from 304, exactly the 16 new ones).
- **`sudo -E` is not a given.** On the GitHub runner, `sudo -E` prints "preserving the entire environment is not supported" and carries on without it, so compose saw no variables. Passing them on the `sudo` line (`sudo VAR="$VAR" docker ...`) works.
- **A brand-new registry package can refuse its first push.** On main, every layer of the new `lf-manager` image uploaded, then GHCR denied the manifest; the package had been created and linked to the repo seconds before. Re-running just the failed job fixed it. The incident workflow opened #82 within a minute, and it was closed with that evidence.
- **Pass numbers:** 3 PRs merged (#74, #75, #78) in about 90 minutes, 5 reviewer rounds across 3 PRs, 2 follow-up issues filed from non-blocking findings, 1 incident opened and closed.

## Guardrails moved from prompt to hook (2026-11-15)
- A peer session's lesson from another factory: "safety by prompt isn't safety". The factory's rules (no direct server SSH, owner-only secrets, no force push) were only instructions. The transcripts showed it never broke them, but nothing stopped it.
- Now a PreToolUse hook, `factory_guard.py`, blocks those actions in factory runs. It is loaded from the main checkout, so a pass can't edit its own guard. Proof by behaviour: a real headless Claude run tried an SSH and a `gh secret set`. Both were blocked, the agent didn't look for another way in, and the secret doesn't exist.
- A trap found while testing: a hook whose script is missing makes Python exit 2, and exit 2 means "block". One missing file would have stopped every tool call. Observability hooks must fail open (`|| true`); guard hooks must fail closed.

## The first real deploy (2026-11-15, pass lf-b3e19)
- **The exam fixed the interface before any code existed.** The exam writer had to invent the server script's contract: env names, a `NAME=value` stdin protocol for secrets, and the exact docker command forms its stub understands. It then proved the exam satisfiable against a throw-away reference implementation kept outside the repo, so the implementer started with a known-passable target: 47 of 47 on the first full run.
- **A reviewer found what the tests could not.** Round 1 found two real risks no unit test would show. A manual "deploy this sha" could run an unmerged branch's script as root. And `docker login` on the server would have overwritten (and `logout` deleted) root's shared registry login, used by the owner's other services. The fixes were a `git merge-base --is-ancestor` check and a throw-away `DOCKER_CONFIG`, each a few lines.
- **`GITHUB_SHA` means different things per trigger.** In a `workflow_run` it is main's head when the event fired, not the commit CI tested. That turned into a free guard: if they differ, a newer commit is coming, so skip. An older CI run can never roll production back.
- **First deploy, first try:** 35 seconds on the server. Migrations applied against the real database, two nginx blocks swapped with `nginx -t` and backups, and the outside check (`/api/health` → `database: ok`) green. The owner's other sites stayed up.
- **Pass numbers:** 2 PRs merged (#80, #83), 2 review rounds, 2 follow-up issues, 3 new owner items, about 105 minutes, of which about 25 went to writing a 54-test exam.

## The live terminal smoke (2026-11-15, pass lf-c7d42)
- **A synthetic student instead of a stored secret.** The live smoke needed a student who can log in, and no admin API existed yet. A new CLI upserts a dedicated `lf-smoke` cohort, the workflow generates a fresh class password per run (masked, sent on stdin only), and the student is disabled again at the end of every run. There is nothing for the owner to install, and nothing worth stealing.
- **The docker exam found a production bug, not a test bug.** The client opened the WebSocket right after the lab started, before ttyd listened, and got a 502. The race was in the exam's harness, but the same thing can happen live. The fix went in the client: retry 502/503/504 until the timeout, and fail at once on anything else.
- **The reviewer read GitHub's queueing rules better than the code did.** A concurrency group keeps only one pending run, so an automatically queued smoke can cancel a pending Deploy. Within ten minutes the live pipeline showed a cousin of that bug: a smoke that ran after a Deploy which skipped a stale sha failed against the old image (a false red). The next run, after the real deploy, was green. Both cases became #90, with the post-deploy smoke moved inside the Deploy run (D38).
- **The guard hook is a substring matcher, and it showed.** Two harmless commands were blocked because the heredoc text of a decision and of a PR body contained the word "SSH". Writing those texts with the file tool first, then committing, went through. This is a false positive the D35 entry predicted ("a pattern check stops mistakes, not an adversary").
- **Small wins:** the reviewer checked that a hash pin was the right wheel in `uv.lock`. An exam writer caught a wrong lab id in the manager's own decision (`sample/hello` is the folder; the id is `hello`).
- **Pass numbers:** 1 PR merged (#87) and proven live through the public URL, 1 PR open (#91), 3 decisions (D36–D38), 4 new issues (#88, #89 from slicing #9; #90 from review), about 95 minutes.

## The throttle that ate the last frame (2026-11-15)
The owner said "factory is offline", but nothing had failed. Pass 8 had ended cleanly. The live-view publisher had been capped at one push per 15 s, so it wouldn't trip the server's SSH rate limit, and it quietly dropped the "pass ended" event that came 6 s after the previous push. The page kept saying "running", and two minutes later "offline". The fix was one flag: the final push of a pass is forced. **Lesson:** a throttle must never drop the *last* state. Coalesce events, never discard them. A second lesson: the page's own acceptance tests pin "offline = no update for 2 minutes", so the fix belongs on the publisher side (a 1-minute heartbeat), not in the page.

## Copy the server, don't merge into it (2026-11-15)
The nginx config lives in two places: the server, where the factory installs its blocks, and a separate infra repo whose pipeline overwrites the server on every push. Instead of hand-editing the repo copy, Claude pulled the live file, diffed it against the repo (only the factory's two blocks differed), and committed the server's bytes verbatim. It also checked `docker compose up --dry-run` beforehand, to make sure the pipeline would only restart nginx, not recreate it. The deploy then rewrote the server with what was already there. Every site stayed up, and nginx kept its address.

## Borrowing a design, not the code (2026-11-15)
The owner wanted the factory page to show every agent and subagent the way a sibling project's QA view does. That project's code lives in a company repo, so the other Claude session sent a design description over cross-session messaging and asked us not to read its code. The design was "read Claude Code's own transcripts, no hooks". Claude rebuilt it from that description. A subagent's parent is the transcript that holds the `tool_use` whose id is in its `.meta.json`. "Running" means a `tool_use` with no `tool_result` yet. Labels come from an allow-list (the call's own short `description`), never from inputs or outputs. A test plants secrets in fake transcripts and asserts that none of them reach `live.json`.

## Deploying when CI can't run (2026-11-15)
The free 2,000 Actions minutes ran out mid-afternoon, and GitHub refused every job. The factory noticed it by itself, opened incident #96, and switched to local-only work (D41). For the static dashboard, the "deploy without CI" path was simply the workflow's own steps run from the laptop:
1. Run the full test suite and acceptance exam locally (141 + 160 + 69 tests).
2. Merge the PR.
3. Build `snapshot.json`.
4. Stream the five files over one SSH connection with `tar | ssh`, then do the same `mv` from `.incoming` that the workflow does.

The lab app itself stays blocked. Its exam needs Linux and gVisor, which a Windows laptop can't stand in for.

## The factory audits its own bill (2026-11-15)
After the minutes ran out, the manager pass did not just file an owner ticket. It pulled 737 workflow runs from the API, re-billed every job the way GitHub does (rounded up per job), and found the surprise: **the factory's own bookkeeping was the biggest cost**. 886 of ~1,860 minutes were full CI runs (gVisor docker job included) started by docs-only state commits to `main`. The fix became issue #98, which got the same treatment as any feature: exam first (21 tests, including a throwaway git repo that proves "code commit, then a docs commit, still deploys the code"), then code, then a fresh-context review. All of it was done with zero CI minutes, and it waits to be merged first once CI is back.
Tip: when an autonomous loop hits a budget wall, ask it to measure before it asks for more budget. The owner's O16 now says what a factory day costs (~900 min, ~$5) and what the fix saves.
